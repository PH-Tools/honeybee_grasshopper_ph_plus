# planning/ — working plans and in-flight work

Tracked planning material for HBPH+. Distinct from `context/` (stable canon).

> **Cross-repo canon:** the BLDGTYP `planning-conventions` skill defines the shared contract (folder shapes, status vocabulary, flat-by-slug archiving, GitHub issue workflow). This file is the contributor-readable contract for this repo; deviations declared here win for this repo.

## Source-of-truth rules

1. **Plans are provisional; `context/` is canonical.** When a plan lands, fold the outcome into the relevant `context/` doc.
2. **`STATUS.md` is the index.** Every active item gets a row.
3. **One folder per unit of work**, lowercase kebab-case.

## Layout

```
planning/
  README.md          # read order
  STATUS.md          # master index of active work
  features/          # new-capability plans   (features/<slug>/)
  bug-fixes/         # defect investigations  (bug-fixes/<slug>.md, or <slug>/ if large)
  archive/           # completed/superseded    (archive/<slug>/ + README index)
```

For small items — most bug fixes — a single `<slug>.md` is enough; use the folder contract
below only when the work needs a separate PRD and plan.

## Feature folder contract

```
<slug>/
  README.md   # router: scope, read order
  PRD.md      # what/why
  STATUS.md   # current state, next step, blockers
  PLAN.md     # optional implementation sequence
```

## Archiving completed work

When an item is `Complete`/`Superseded`: fold the outcome into `context/`, then **move** its folder to `planning/archive/<slug>/` unchanged and add a row to `planning/archive/README.md`. Flat by slug, never nested by date. (The existing `archive/ph-navigator-v1/` follows this shape.)

## GitHub issue workflow

Issues are the intake and the permanent index; `planning/` files are the working record.

- **Issue-first:** every unit of work gets a GitHub issue when it becomes real work — at
  intake for bugs and requests, at scoping for features. The issue body is a sanitized
  summary (what, why, acceptance shape), not the PRD.
- **Issue-only by default:** small items need no planning doc at all. Create one only when
  the work needs more than the issue body carries well: multi-phase or cross-repo plans an
  agent executes from, evidence that cannot be public, or heavy working state.
- **Linkage:** issue body → packet path; packet `STATUS.md` → issue URL; PR description →
  `Closes #N`; archive README row → closed-issue link.
- **Files, not threads:** PRDs, phase plans, status ledgers, and root-cause evidence live
  here, not in issue comment threads.
- **Public repo:** client names, BT numbers, project data, and PHI/Phius/PHPP-licensed
  content never appear in issue text or planning docs. Reference client evidence
  generically ("a production project model").

## Status vocabulary

`Requested` · `Scoped` · `In progress` · `Blocked` · `In review` · `Implemented on branch` · `Merged to main` · `Complete` · `Deferred` · `Superseded`.
